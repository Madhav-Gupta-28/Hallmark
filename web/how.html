The mechanism

How it works

One invariant, four signed numbers, and the amount that actually arrived. No oracle, no price feed, no cross-contract call, nothing to keep running. This page is the whole of it — the arithmetic, the hole we found in our own live contract, the surface that enforces it, and the agents that compete to be refused.

A fill, step by step

The filler delivers the output first. That is the load-bearing decision.

Watch where the money is at each step. The output is inside the vault before the input is credited to anybody, so there is no interval in which either side is exposed — and no cross-contract call in the verification path, so there is nothing to roll back.

step 1 of 9

No unsigned field is trusted

depositAddress is never used, because the vault never sends the owner's funds anywhere a filler nominated.

No attribution problem

The delivered amount is a function argument, not a balance delta — so concurrent fills cannot be confused, and no filler can claim another's delivery.

No custody window

Step 5 completes before step 8 begins. Nobody ever holds a counterparty's funds, so there is nothing to misappropriate and nothing to unwind.

The cost of this choice, stated. The filler must front the output, so it needs destination-asset inventory or must source it first and carry the price risk in between. That is what a dealer does, and it is the price of closing a hole that cannot otherwise be closed.

The invariant, worked on real fixtures

Both USD marks are inside the signed payload, so the contract reads bytes it was handed and does integer arithmetic. Pick a fixture; the numbers are the file's, and the contract column is a live view call.

Canonicalisation, deleted rather than solved

Re-serialising JSON inside a contract to re-derive a hash is a reliable way to lose a week: Rust and TypeScript must agree byte-for-byte on key order, number formatting and unicode escaping, forever.

Hallmark has no canonicalisation code in Rust at all. The client builds the canonical byte string; the contract is handed those exact bytes and does this: 

sha256(bytes)
  → base58
    → ed25519_verify(sig, that string, signer)
      → from_slice(THE SAME bytes)

Hash first, parse second, same bytes both times. If a single byte differs from what the venue signed, verification fails before any field is read. every_single_byte_is_covered_by_the_signature asserts it by flipping each of the 692 bytes in turn.

The signature is over the UTF-8 of the base58 string of the digest, not over the digest. This is the single most load-bearing implementation detail in the project; getting it wrong produces a verifier that rejects every real quote.

The canonicaliser exists three times, on purpose

whereimplementation
fixtures/mkfix.pyPython + from-scratch RFC-8032 ed25519
client/src/lib/canonical.tsTypeScript, json-stable-stringify
web/assets/hallmark.js~20 lines of browser JS, no dependency

All three agree, byte for byte and hash for hash, on all three fixtures. Three independent implementations agreeing is meaningfully stronger evidence than one being carefully written.

Rounding has exactly one safe direction

Every truncation must make the reported cost larger, never smaller — a bound that understates cost is not a bound.

steproundseffect on reported cost
parse_fixed(amountOutUsd)downunderstates the output's value → cost up ✓
value_ratio = outUsd·1e9/inUsddowncost up ✓
fill_ratio = delivered·1e9/amountOutdowncost up ✓
kept = value·fill/1e9downcost up ✓
bps = shortfall/1e9must round UP← the one that needed fixing
Found by running the code, not by reasoning about it. The final division was truncating. On the honest fixture the exact cost is 159.348 bps; truncation reported 159, understating the bound. It now uses div_ceil and reports 160. Pinned by the_reported_cost_is_never_below_the_true_cost, which asserts both reported ≥ exact and reported − exact < 1.0.
256-bit intermediates are not optional. wNEAR has 24 decimals, so a $1M order is ~1e30 base units and delivered × 1e9 is ~1e39 — which overflows u128 (max ≈ 3.4e38). mul_div computes a·b as a 256-bit (hi, lo) pair and does restoring long division, 128 iterations.

02 · the hole we found

The free option we wrote against our own users

v1 was live on mainnet with a hole that defeated the headline claim.

The bound is denominated in amountInUsd and amountOutUsd. Those numbers were true when the venue signed, and not necessarily now. v1's only freshness check was the quote's own deadline: 

// v1
if now_secs >= deadline_secs {
  return Err(Refusal::QuoteExpired { .. })
}

deadline is supplied by whoever requests the quote, and 1Click signs it unquestioned. Measured live on 2026-11-01: 

asked      signed?   valid for
+   1 day    true        1 day
+  30 days   true       30 days
+ 365 days   true      365 days
+3650 days   true    3650 days

Ten years. And dry:true quotes are free, unauthenticated, and still signed. So the attack costs nothing to set up:

  1. Ask for a quote matching an open mandate, deadline years out. Free.
  2. Do it repeatedly and keep them. You now hold a library of free options on the owner's escrow, each struck at the prices of the day it was minted.
  3. Wait. When the market moves, exercise whichever became profitable.
  4. The vault prices it from the quote's own frozen marks, reports a number inside the ceiling, and releases the escrow.

The owner's max_cost_bps was enforced exactly — against a market that no longer existed. The realised loss is the whole adverse move and is unbounded.

↳ a three-day-old quote, validly signed and three days inside its own deadline, priced at three-day-old USD marks. Allowed.

The fix was a field already inside the signature

timestamp — when the venue signed — was in the canonical bytes all along. v1 simply never read it.

// v2 onwards
let signed_at = parse_iso8601_secs(&q.timestamp);
if now_secs > signed_at + m.max_quote_age_secs {
  return Err(Refusal::QuoteTooOld { .. })
}

Being signed and being trustworthy are different properties. timestamp is written by the venue. deadline is written by the counterparty. The same reasoning already rejected depositAddress — this is it applied one level deeper than v1 applied it.

How fresh do you insist on?

This is the real control an owner has. Drag max_quote_age_secs — the one number v1 did not have — and watch where the bound falls relative to how old this fixture actually is. And a real transaction, not a simulation

A quote was banked for 326 seconds against a 300-second bound, then a fill was actually broadcast with real USDT. The vault refused it and the tokens came back.

A refused fill is a successful transaction. NEP-141 catches the receiver's panic in order to make the refund work, so the outer status is SuccessValue and the refusal is buried in an inner receipt. Anything reporting on a fill has to read receipts_outcome — our own reference filler called a refused fill a filled one until this was found.

Exact cost 159.348 bps; the contract reported 159. A bound that understates cost is not a bound. Found by running the arithmetic, not reading it.

the storage bug, twice

A fixed byte charge left the vault paying for strangers' state. The first fix refunded more than it freed, so open-and-cancel in a loop still drained it. Both caught by printing real byte counts.

03 · the contract

Twenty-three exported methods, nine typed refusals, sixteen invariants, and one path that moves value. No admin key, no pause, no upgrade path — and no oracle, because the price authority is the counterparty's own signature.

One path moves value

Every state change that moves a token starts in ft_on_transfer, which NEP-141 calls when somebody ft_transfer_calls into the vault. That single call carries everything verification needs:

fromthe vault learns
env::predecessor_account_id()which token arrived
sender_idwho sent it
amounthow much arrived
msgthe canonical quote bytes, the signature, the mandate id

Synchronous, with no cross-contract call — so there is no rollback path, no in-flight record and no stuck state. Payouts are pull, not push, which keeps the verification path free of promises entirely and means a counterparty who is not storage-registered on a token cannot brick a fill for anybody else.

Which action is legal depends on which token arrived

actionlegal tokeneffect
openthe mandate's origincreate a funded mandate
fundthat mandate's origintop up the escrow
fillthe destinationthe transfer is the delivery

↳ so an action cannot be performed with the wrong asset. Calling ft_on_transfer directly gets you an asset id derived from your own account — which is why that attack is refused with “this token is not the mandate's destination asset”.

What the owner commits to

Four numbers and two assets. No policy language, no allowlist, no per-protocol configuration — a reader who knows nothing about Intents can audit this in ten seconds, which is deliberate. A bound nobody can read is a bound nobody trusts. 

pub struct Mandate {
    pub origin_asset:        String,   // nep141:…

}                                      //   cannot silently lose precision

Whoever causes a byte to be written pays for that byte

NEAR stakes part of an account's balance per byte of state it holds, so somebody has to pay for a mandate's record. v1's answer was the vault, which gave a stranger about ten times leverage against it: roughly ten cents of gas and a live vault could no longer write state at all — fills and withdrawals included.

v2 charged a fixed 1,536 bytes. That was also wrong: it overcharged honest owners and still left a hole for a mandate with more fillers than the fixed allowance covered. And its first version refunded more on cancel than it actually freed, so open-and-cancel in a loop drained the vault anyway, just slower.

v3 stops guessing. One helper runs at the end of every path that writes state: flush the collections, diff env::storage_usage(), and charge the caller exactly that — or credit them exactly what shrank. 

fn settle_storage(&mut self, who: &AccountId, before: u64) {
    self.mandates.flush();
    self.open_ids.flush();
    self.credits.flush();
    let after = env::storage_usage();
    if after > before {
        let owed = bytes_to_near(after - before);
        require!(balance >= owed, "prepay storage first: …");
        // deduct
    } else if before > after {
        // credit back bytes_to_near(before - after)
    }
}
A trap inside the trap. near_sdk::store collections buffer their writes and flush when the call ends, so storage_usage() immediately after a remove still reports the old figure — and the refund came out as zero. Hence the explicit flush.

The suite is deterministic, and that took two fixes. Each integration test starts a real nearcore node, and at cargo's default parallelism 28 of them raced for ports until one died inside PeerManagerActor::spawn. Separately, a patched account's state lands before the node has indexed its access key, so an immediate call failed with “access key … has never been observed”. Both were intermittent and both were found by running the suite repeatedly rather than once. “Clone it and run the tests” is the whole claim; a suite that fails one run in three does not support it.

The toolchain trap, which costs a day if you meet it late

nearcore's VM only accepts MVP WebAssembly. From rustc 1.87 on, the output is unusable — and the failure mode is the trap: DeployContract succeeds, because deploying does not compile the module. Every subsequent call fails with CompilationError(PrepareError(Deserialization)). -C target-cpu=mvp is not sufficient, because the prebuilt std was compiled with the newer features regardless.

The race, on mainnet

One live signed quote, one second old, three agents. All three inside the owner's ceiling, disagreeing only about strategy — which is the whole claim: the mandate does not care who fills it.

Competition acts on the right variable. A filler that delivers more lowers the owner's cost and still profits. The cheapest of the three here is the adapted official agent, at 69 bps against a 300 bps ceiling.
And the limit, stated. First-come-first-served means whoever lands first wins, not whoever is cheapest. The owner gets their ceiling, not the best price in the market. An auction window — collect deliveries for N blocks, settle the best — is the natural next version and is not claimed for v1.

Turning NEAR's own agent into a filler

The starting point is near/agent-skills, skill near-intents, rules/server-example.md — the file NEAR ships for an agent that needs to do a swap from a script. Install it the way an agent would: 

npx skills add near/agent-skills --skill near-intents

Its flow, verbatim from the skill: fetchTokens → getQuote(dry:false) → send deposit to quote.depositAddress → submitDeposit → pollStatus. Below is that same flow with four changes, and nothing else. They are marked [1]..[4] in the source.

01
is told what to swap
reads get_mandates() — a keyless view — and takes the pair, the size and the ceiling from the mandate. The work comes from the chain.
02

recipient is the vault. recipient is inside the signature, so a quote addressed anywhere else is refused WrongRecipient.
03

dry: true, then sends the destination asset to the vault with the signed quote in msg. The load-bearing one. depositAddress is not covered by the signature, so a filler should not trust it and the vault must not.

neither — the fill settles inside ft_on_transfer, so the receipt is the terminal state. Nothing to poll, nothing in flight.

Unchanged: the API base, the quote request shape, slippageTolerance, asset ids from /v0/tokens, and reading amountOut / minAmountOut off a signed quote. An agent that already speaks 1Click keeps all of it.

The official flow uses 1Click as an execution venue. A filler uses it as a price oracle whose word can be proved. Same API, opposite direction of trust.

And one change that is not an adaptation at all — a [0] fix, because the official example does not run. Its getQuote sends only dry, swapType, slippageTolerance and its five parameters. Against the live API on 2026-11-02 that is HTTP 400: depositType should not be empty … refundType should not be empty … recipientType should not be empty … deadline must be a valid ISO 8601 date string. The skill's own api-quote.md documents all four with defaults — ORIGIN_CHAIN, DESTINATION_CHAIN, ORIGIN_CHAIN, ~10 min — which is presumably why the example omits them. The network requires them. An agent following the skill as written fails its first quote.

↳ found by running the official example rather than reading it — the same discipline that found both exploits. Where documentation disagrees with the network, the network wins, and the disagreement gets recorded.

Why a stranger would bother

The spread is the whole fee, so there is no fee field

Because the filler delivers an amount of its own choosing — at or above the quote's signed floor — its compensation is simply what it keeps: the gap between what it could source the output for and what it delivered.

That number is already inside the owner's ceiling, because the ceiling is enforced on the realised cost. So the mandate needs no fee field, no fee rail, no fee accounting and no second asset. An earlier draft had a max_filler_fee_bps paid on proven delivery; once the filler delivers first that is double-paying, and the field was built, tested, and then deleted.

For scale: 1Click's own rake is 20 bps, inserted unprompted into every quote. That is the right anchor for judging whether a filler's spread is reasonable.

The capital requirement is real, and is the price of closing the hole

A filler must front the output. Two ways, both legitimate:

  • Inventory. Hold the destination asset and quote against it. Lowest latency, highest capital.
  • Source-then-deliver. Buy the output via 1Click (depositType: INTENTS, ~10 s), then deliver it. Two transactions, and the filler carries the price risk in between — which is exactly the risk it is being paid the spread to carry.

A filler also prepays storage, because a fill creates credit slots and whoever creates state pays for it. One deposit, reusable, measured in thousandths of a NEAR.

The second incentive works at zero volume

Every fill emits a receipt bound to the filler's account, so a filler accumulates a provable execution record rather than a self-reported one. A new agent developer wants fills in order to build a track record they can later sell. The receipt already exists; indexing it by filler costs almost nothing.

What is not claimed. There is no third-party filler ecosystem. Three fillers, all written by us or adapted by us, and this page does not pretend otherwise. What the three do demonstrate is that the mandate does not care who fills it, and that an independent reading of the invariant agrees with the chain on live quotes.
