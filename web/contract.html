The contract

Twenty-three exported methods, nine typed refusals, sixteen invariants, and one path that moves value. No admin key, no pause, no upgrade path — and no oracle, because the price authority is the counterparty's own signature.

One path moves value

Every state change that moves a token starts in ft_on_transfer, which NEP-141 calls when somebody ft_transfer_calls into the vault. That single call carries everything verification needs:

fromthe vault learns
env::predecessor_account_id()which token arrived
sender_idwho sent it
amounthow much arrived
msgthe canonical quote bytes, the signature, the mandate id

Synchronous, with no cross-contract call — so there is no rollback path, no in-flight record and no stuck state. Payouts are pull, not push, which keeps the verification path free of promises entirely and means a counterparty who is not storage-registered on a token cannot brick a fill for anybody else.

Which action is legal depends on which token arrived

actionlegal tokeneffect
openthe mandate's origincreate a funded mandate
fundthat mandate's origintop up the escrow
fillthe destinationthe transfer is the delivery

↳ so an action cannot be performed with the wrong asset. Calling ft_on_transfer directly gets you an asset id derived from your own account — which is why that attack is refused with “this token is not the mandate's destination asset”.

What the owner commits to

Four numbers and two assets. No policy language, no allowlist, no per-protocol configuration — a reader who knows nothing about Intents can audit this in ten seconds, which is deliberate. A bound nobody can read is a bound nobody trusts.

The exported surface

Checked by extracting every pub fn from the #[near] impl and diffing it against this table: 23 in the code, 23 documented, nothing undocumented. The twelve views are the proof surface — every guarantee in the specification can be exercised with no key, no funds and no deposit.

Two views deliberately do not check the signature. worst_cost and realised_cost price whatever bytes they are handed — that is what makes them useful on a quote you are still deciding about, and it is why dry_check, which does verify, is the one a filler consults before spending anything.

Whoever causes a byte to be written pays for that byte

NEAR stakes part of an account's balance per byte of state it holds, so somebody has to pay for a mandate's record. v1's answer was the vault, which gave a stranger about ten times leverage against it: roughly ten cents of gas and a live vault could no longer write state at all — fills and withdrawals included.

v2 charged a fixed 1,536 bytes. That was also wrong: it overcharged honest owners and still left a hole for a mandate with more fillers than the fixed allowance covered. And its first version refunded more on cancel than it actually freed, so open-and-cancel in a loop drained the vault anyway, just slower.

v3 stops guessing. One helper runs at the end of every path that writes state: flush the collections, diff env::storage_usage(), and charge the caller exactly that — or credit them exactly what shrank. 

fn settle_storage(&mut self, who: &AccountId, before: u64) {
    self.mandates.flush();
    self.open_ids.flush();
    self.credits.flush();
    let after = env::storage_usage();
    if after > before {
        let owed = bytes_to_near(after - before);
        require!(balance >= owed, "prepay storage first: …");
        // deduct
    } else if before > after {
        // credit back bytes_to_near(before - after)
    }
}
A trap inside the trap. near_sdk::store collections buffer their writes and flush when the call ends, so storage_usage() immediately after a remove still reports the old figure — and the refund came out as zero. Hence the explicit flush.

Who pays for what

callcharged to
openthe owner — record + index entry
fillthe filler — the credit slots it creates
fundnothing — it writes no new state
cancelthe net: index entry out, maybe a credit slot in
withdrawrefunds the slot — but only once the payout lands
reaprefunds exactly what deleting the record frees

The order book costs what the vault holds, not what it remembers

v1 and v2 answered get_mandates by walking every mandate ever created and discarding the closed ones. Correct, and it gets slower forever: with fifty thousand mandates the call has to load and decode fifty thousand records to hand back fifty, and a view call has a gas budget. Past some size the only way a filler can find work stops answering at all — and so does this website.

Not a security hole: with storage prepaid, nobody can inflate that number cheaply. It is a wall you only hit by succeeding, which is exactly why it was worth removing before launch rather than after.

What it costs to run, and what proves it

a whole fill, on mainnet
30.48 TGas
every receipt in the transaction — the filler's ft_transfer_call, the token's hop, sha256 + ed25519_verify, the invariant, and both credits. 10% of one transaction's limit.
the verification itself
7.8 TGas
measured in the sandbox, counting only the fill's own burn. Nothing in the path scales with anything but the length of the signed quote.
tests, from a clean clone
58 + 54
30 unit + 28 against a real sandbox node, plus 54 client assertions. No network, no key, no funds.
The suite is deterministic, and that took two fixes. Each integration test starts a real nearcore node, and at cargo's default parallelism 28 of them raced for ports until one died inside PeerManagerActor::spawn. Separately, a patched account's state lands before the node has indexed its access key, so an immediate call failed with “access key … has never been observed”. Both were intermittent and both were found by running the suite repeatedly rather than once. “Clone it and run the tests” is the whole claim; a suite that fails one run in three does not support it.

The toolchain trap, which costs a day if you meet it late

nearcore's VM only accepts MVP WebAssembly. From rustc 1.87 on, the output is unusable — and the failure mode is the trap: DeployContract succeeds, because deploying does not compile the module. Every subsequent call fails with CompilationError(PrepareError(Deserialization)). -C target-cpu=mvp is not sufficient, because the prebuilt std was compiled with the newer features regardless.
