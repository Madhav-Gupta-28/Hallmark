Mechanism

How it works

Four things carry the whole design: one expression over signed fields, an inverted order of operations, a hash computed before anything is parsed, and a rounding direction. Everything else is consequence.

A fill, step by step

The filler delivers the output first. That is the load-bearing decision.

Watch where the money is at each step. The output is inside the vault before the input is credited to anybody, so there is no interval in which either side is exposed — and no cross-contract call in the verification path, so there is nothing to roll back.

step 1 of 9

No unsigned field is trusted

depositAddress is never used, because the vault never sends the owner's funds anywhere a filler nominated.

No attribution problem

The delivered amount is a function argument, not a balance delta — so concurrent fills cannot be confused, and no filler can claim another's delivery.

No custody window

Step 5 completes before step 8 begins. Nobody ever holds a counterparty's funds, so there is nothing to misappropriate and nothing to unwind.

The cost of this choice, stated. The filler must front the output, so it needs destination-asset inventory or must source it first and carry the price risk in between. That is what a dealer does, and it is the price of closing a hole that cannot otherwise be closed.

Canonicalisation, deleted rather than solved

Re-serialising JSON inside a contract to re-derive a hash is a reliable way to lose a week: Rust and TypeScript must agree byte-for-byte on key order, number formatting and unicode escaping, forever.

Hallmark has no canonicalisation code in Rust at all. The client builds the canonical byte string; the contract is handed those exact bytes and does this: 

sha256(bytes)
  → base58
    → ed25519_verify(sig, that string, signer)
      → from_slice(THE SAME bytes)

Hash first, parse second, same bytes both times. If a single byte differs from what the venue signed, verification fails before any field is read. every_single_byte_is_covered_by_the_signature asserts it by flipping each of the 692 bytes in turn.

The signature is over the UTF-8 of the base58 string of the digest, not over the digest. This is the single most load-bearing implementation detail in the project; getting it wrong produces a verifier that rejects every real quote.

All three agree, byte for byte and hash for hash, on all three fixtures. Three independent implementations agreeing is meaningfully stronger evidence than one being carefully written.

Rounding has exactly one safe direction

Every truncation must make the reported cost larger, never smaller — a bound that understates cost is not a bound.

steproundseffect on reported cost
parse_fixed(amountOutUsd)downunderstates the output's value → cost up ✓
value_ratio = outUsd·1e9/inUsddowncost up ✓
fill_ratio = delivered·1e9/amountOutdowncost up ✓
kept = value·fill/1e9downcost up ✓
bps = shortfall/1e9must round UP← the one that needed fixing
Found by running the code, not by reasoning about it. The final division was truncating. On the honest fixture the exact cost is 159.348 bps; truncation reported 159, understating the bound. It now uses div_ceil and reports 160. Pinned by the_reported_cost_is_never_below_the_true_cost, which asserts both reported ≥ exact and reported − exact < 1.0.
256-bit intermediates are not optional. wNEAR has 24 decimals, so a $1M order is ~1e30 base units and delivered × 1e9 is ~1e39 — which overflows u128 (max ≈ 3.4e38). mul_div computes a·b as a 256-bit (hi, lo) pair and does restoring long division, 128 iterations.

An SDK check binds the honest agent and not the compromised one. A prompt-injected agent simply does not call the SDK. This is the single most common shape of a wrong answer to this problem.
TreasuryPilot moves the trust rather than removing it. Its EIP-712 quotes, nonce, expiry and route hash are all correct — but the signer is one the project controls. If that signer lies, the treasury is drained with a valid signature.
